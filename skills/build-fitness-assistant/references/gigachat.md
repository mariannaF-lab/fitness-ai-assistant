# GigaChat API

## Настройка

Проверяй текущие endpoints, модель, scope, SDK и сертификаты в официальных документах:
- https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api
- https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-token
- https://developers.sber.ru/docs/ru/gigachat/guides/using-sdks
- https://developers.sber.ru/docs/ru/gigachat/tariffs/individual-tariffs

У пользователя выбран GigaChat; наличие страницы примера или созданного ключа не доказывает успешность обращения к API, доступность конкретной модели или остаток бесплатных токенов. Проверяй это фактическим минимальным запросом после настройки секрета. Не покупай пакет автоматически.

Authorization key — исходные данные авторизации. Access token — временный токен; в исходном сценарии срок 30 минут, в реализации ориентируйся на срок, возвращённый API. Не проси пользователя вручную менять Access token каждые полчаса.

Предложенная конфигурация `.env.example`:

```dotenv
GIGACHAT_CREDENTIALS=
GIGACHAT_MODEL=
GIGACHAT_SCOPE=
TELEGRAM_BOT_TOKEN=
DATABASE_URL=sqlite:///./data/fitness.db
```

Конкретные имена согласуй с выбранным SDK. Секрет пользователь вводит локально; не проси вставлять его в чат. Исключи `.env`, локальную базу, журналы и файлы сессий из Git до первого коммита. Для собственного сертификата используй корректную цепочку доверия; не отключай TLS-проверку ради обхода ошибки.

## Адаптер

- Вынеси API в отдельный модуль с операциями генерации, объяснения и адаптации.
- Используй официальный SDK, если он корректно решает авторизацию и соответствует текущему API, либо явный HTTP-клиент.
- Получай токен при необходимости, обновляй до истечения. При одновременных запросах избегай конкурирующего обновления.
- После ошибки истечения авторизации допустимо одно обновление и одна повторная попытка. Постоянный 401/403 покажи как ошибку настройки, без цикла повторов.
- Для 429/временных сетевых ошибок установи ограниченное число повторов с задержкой, учитывай Retry-After и общий timeout. Не повторяй безусловно запрос после неопределённого сетевого исхода: возможен дополнительный расход токенов.
- Некорректную структуру ответа разрешается исправлять одним дополнительным запросом. Повторная ошибка завершает операцию, не создаёт готовую программу.
- При ошибке сохраняй профиль и возможность повтора, убирай индикатор ожидания. Не показывай пользователю сырые исключения с заголовками авторизации.

## JSON и проверка

Общий результат: status = ready / needs_clarification / requires_professional_review, message, questions, program. При ready program обязателен; при остальных статусах program = null. Для объяснений и адаптации используй отдельные схемы; не пытайся поместить объяснение в поле program.

Проверь поддержку JSON-schema/structured output у выбранного endpoint и модели. Если её нет, запроси JSON текстом, разбери и проверь через Pydantic. Не выдавай этот способ за гарантию соблюдения схемы.

Проверяй типы, обязательные поля, конечность чисел, положительные подходы/повторения, неотрицательный отдых, количество занятий и временной бюджет. Длительность учитывает отдых и все части занятия. Оборудование проверяй по нормализованным категориям; не обещай полную содержательную валидацию свободного текста. Не исправляй сомнительную программу молча.

Сохраняй модель, версию промпта, дату, статус и доступные метрики расхода без сырого профиля в технических логах. Ограничивай размеры входных полей и ответа, не передавай всю историю без необходимости.
